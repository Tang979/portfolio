Decoupled Logic & View Layer

1. The Philosophy of Separation

The core of this architecture lies in the strict application of the Separation of Concerns (SoC) principle. The project is divided into two absolute independent boundaries:

  • Domain Layer (Pure C#): Acts as the “Brain,” containing all core rules, states, and game algorithms. This layer has zero dependencies on UnityEngine.dll.
  • Unity Infrastructure (View Layer): Acts as the “Body,” responsible for visual rendering, audio, and capturing user input.

3. Domain Layer: Pure C# Logic

All game entities (Enemy, Tower, HexMap) are defined as pure C# classes. This ensures that game logic runs consistently regardless of the engine’s frame rate and remains highly accessible for Unit Testing.

Illustration from Enemy.cs: This class manages attributes like health and speed without using any Unity components.

namespace Domain.Entities
{
    public class Enemy
    {
        public string Id { get; }
        public float MaxHealth { get; private set; }
        public float CurrentHealth { get; private set; }
        public float CurrentSpeed => BaseSpeed * SpeedModifier; // Calculated purely via logic

        public void TakeDamage(float amount)
        {
            CurrentHealth -= amount; // Pure health subtraction logic
        }
        
        public void Tick(float deltaTime)
        {
            // Handles status effects like Burn or Slow independently of the Engine
        }
    }
}

4. View Layer: Unity Infrastructure

View classes (inheriting from MonoBehaviour) serve as the visual shell. They do not calculate logic; instead, they reflect (State Mirroring) the state of the Domain Layer onto the screen.

Illustration from EnemyView.cs: The View only handles visual interpolation and health bar updates based on the Domain’s data.

public class EnemyView : MonoBehaviour
{
    public Enemy Enemy { get; private set; } // Reference to the Domain entity

    void Update()
    {
        if (Enemy.IsDead)
        {
            // Handles only the destruction of the visual object
            Destroy(gameObject); 
            return;
        }

        // Smooth visual interpolation
        var targetPos = _layoutAdapter.HexToWorld(Enemy.NextTile);
        transform.position = Vector3.MoveTowards(transform.position, targetPos, 
                                                Enemy.CurrentSpeed * Time.deltaTime);
    }
}

5. The Synchronization Mechanism

To maintain separation while ensuring smooth visuals, the project utilizes C# Events. The Domain emits events when a state changes, and the View subscribes to these events to update the presentation.

Step 1: Event Declaration in the Domain (Tower.cs)

public event Action<TowerAttackResult> OnAttack; //
// ...
OnAttack?.Invoke(result); // Broadcasts to any listeners

Step 2: Subscription and Unsubscription in the View (TowerView.cs)

public void Initialize(Tower tower)
{
    _tower = tower;
    _tower.OnAttack += HandleAttack; // Subscribe to listener
}

private void OnDestroy()
{
    if (_tower != null)
        _tower.OnAttack -= HandleAttack; // Unsubscribe to prevent Memory Leaks
}

private void HandleAttack(TowerAttackResult result)
{
    // Execute visual effects (Spawn projectile, Sound) only when notified by the Domain
    Instantiate(_bulletPrefab, firePoint.position, Quaternion.identity);
}

6. Technical Advantages

  • Loose Coupling: The View knows about the Domain, but the Domain is entirely unaware of the View. This allows for swapping the entire rendering system without modifying a single line of logic code.
  • Maintainability: Logic errors are isolated in the Domain, while visual bugs are handled in the View, leading to more accurate debugging.
  • Testability: Tower attack logic can be verified in pure C# test projects without requiring Prefabs or GameObjects.
