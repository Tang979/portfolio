Architecture: The Engine-Agnostic Blueprint

1. Design Philosophy & Motivation

In the early stages of development, the system followed a traditional pattern where the entire gameplay logic was Tightly Coupled with classes inheriting from MonoBehaviour. This approach revealed significant limitations in scalability and testability as processing logic became intertwined with the Engine’s lifecycle.

A turning point in my design thinking occurred when I needed to optimize independent testability, leading to a complete restructuring into a Decoupled Architecture. The core objectives were to build a Core Logic capable of:

  • Engine Independence: Gameplay logic operates without any direct dependency on UnityEngine.dll.
  • High Testability: Enabling 100% Unit Testing for critical features (Combat, Pathfinding, Economy) without needing to launch the Unity Editor.
  • Separation of Concerns: Establishing an absolute boundary between the data processing layer and the visual presentation layer.

2. The Layered Breakdown

The project is engineered by combining Domain-Driven Design (DDD) with Clean Architecture, divided into distinct zones of responsibility:

A. Domain Layer (Pure C# - Core Processing Layer)

This is the most critical layer, containing all game operational rules, written entirely in pure C#.

  • Entities (Tower, Enemy, HexMap): These serve as objects containing internal states and rules.

Code Illustration (Enemy.cs): Notice the absolute absence of UnityEngine.

namespace Domain.Entities
{
    public class Enemy
    {
        public string Id { get; } 
        public float CurrentHealth { get; private set; } 
        public float CurrentSpeed => BaseSpeed * SpeedModifier; 

        public void TakeDamage(float amount) => CurrentHealth -= amount; 

        public void Tick(float deltaTime) 
        {
            // Logic for status effects and internal timers 
        }
    }
}
  • Domain Services (EnemyService, PlacementService): These execute complex algorithms, including A* Pathfinding and Deadlock checking.

B. Unity Infrastructure Layer (Presentation Layer)

This layer acts as the execution interface for the Domain, responsible for Visuals and Physics.

  • View Layer (TowerView, EnemyView): These classes inherit from MonoBehaviour but serve a specific role: listening to events from the Domain to update visuals.

Code Illustration (TowerView.cs):

public class TowerView : MonoBehaviour
{
    private Tower _tower; // Reference to Pure C# Domain object 

    public void Initialize(Tower tower, GameObject bulletPrefab, HexTile tile)
    {
        _tower = tower; 
        // Subscribing to Domain events instead of checking logic in Update 
        _tower.OnAttack += HandleAttack; 
    }

    private void Update()
    {
        // Only tells the Domain to update; doesn't calculate damage here 
        _tower.Tick(Time.deltaTime, _enemiesInRange);
    }
}

3. Communication & Data Flow

To maintain a state of Loose Coupling, the project applies industry-standard design patterns:

  • Dependency Injection (DI): Services are initialized and passed via Constructors, facilitating easy replacement with Mock objects during testing.

Code Illustration (EnemyService.cs):

public EnemyService(HexMap map, LaneService laneService, BaseHealthService health, CurrencyService currency)
{
    _map = map; 
    _laneService = laneService; 
    _baseHealthService = health; 
    _currencyService = currency;
}
  • Observer Pattern (Event-Driven): The Domain triggers C# Actions to communicate with the View without knowing it exists.

Code Illustration (Enemy.cs):

public event Action KnockBack; // Pure C# event 
public void TriggerKnockBack() => KnockBack?.Invoke();

4. Composition Root (Lifecycle Management)

Within the Unity Layer, the GameController acts as the Composition Root—the single place responsible for instantiating and connecting all components in the correct dependency order.

Code Illustration (GameController.cs):

// Glue between Domain and Unity Infrastructure 
protected override void Awake() 
{
    base.Awake();
    
    // 1. Initialize Pure C# Services 
    pathfinder = new AStarPathfinder();
    Map = MapLoader.LoadMap(mapJson);
    LaneService = new LaneService(Map, pathfinder);

    // 2. Inject dependencies into Services 
    EnemyService = new EnemyService(Map, LaneService, BaseHealthService, CurrencyService);
    PlacementService = new PlacementService(Map, pathfinder, LaneService);
}

5. Practical Benefits

Implementing a decoupled architecture provides measurable advantages:

  • Debugging Speed: Identifying whether a bug originates in the logic layer or the presentation layer is instantaneous.
  • Performance Optimization: Running logic in pure C# reduces the overhead on the Engine’s update cycle, specifically optimized for mobile devices.
  • Reusability: 80% of the core gameplay logic is entirely independent, ready to be scaled or migrated to other engines without rewriting the game rules.
